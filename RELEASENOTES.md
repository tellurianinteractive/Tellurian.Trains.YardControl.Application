# Release Notes

## Version 2.1.0

### Installing

The archives are self-contained: no .NET runtime is needed. Download the one for your system from the assets below — `win-x64` or `win-arm64` for Windows, `linux-x64`, `linux-arm64` (Raspberry Pi 4/5 on a 64-bit OS) or `linux-arm` (32-bit OS) for Linux — and open `http://localhost:5180` in a browser once the application is running. Other computers and tablets on the layout network use the addresses written to the log at start-up.

**Windows**

1. Extract the zip to a folder, for example `C:\YardControl`.
2. Edit `appsettings.json`: set `CommandStation:Type` to `Z21` (with its `Address`) or `Serial` (with the `PortName`, for example `COM5`, shown in Device Manager). Check `Stations` too.
3. Run `YardController.Web.exe` and allow it on *private networks* when the firewall asks.
4. Stream Deck: plug in the Module, make sure `InputDevice` is `StreamDeck` for the station, and close Elgato's own software if it is running. No driver is needed.

**Linux (including Raspberry Pi)**

1. Install what the key faces need: `sudo apt install fontconfig fonts-dejavu-core`. Without a system font the Stream Deck keys come up blank.
2. Extract and make it runnable:
   ```bash
   sudo mkdir -p /opt/yardcontrol
   sudo tar -xzf YardControlApplication-v2.1.0-linux-arm64.tar.gz -C /opt/yardcontrol
   sudo chmod +x /opt/yardcontrol/YardController.Web
   ```
3. Edit `/opt/yardcontrol/appsettings.json`: set `CommandStation:Type` as above. For a serial interface use `/dev/ttyUSB0` or `/dev/ttyACM0` as `PortName` and add your user to the serial group: `sudo usermod -aG dialout $USER`, then log in again. Write the station paths with forward slashes, `Data/Munkeröd.txt`.
4. Stream Deck: allow non-root access to the Module with a udev rule, then re-plug it:
   ```bash
   echo 'SUBSYSTEM=="hidraw", ATTRS{idVendor}=="0fd9", MODE="0666"' | sudo tee /etc/udev/rules.d/50-streamdeck.rules
   sudo udevadm control --reload-rules && sudo udevadm trigger
   ```
   Without the rule the application still starts; the panel just never appears.
5. Open the port in the firewall if one is running: `sudo ufw allow 5180/tcp`.
6. Run `/opt/yardcontrol/YardController.Web`.

### New features

- **Fictitious signals (information points)** (§6.2.23) — a station file can now declare an *informationspunkt* in `[Signals]` with the type marker `f` (train and shunting routes) or `g` (shunting routes only): a place a route can start or end at where no signal physically stands. Unlike a hidden signal it is drawn, as a diamond with a diamond hole, so it can be clicked. It is coloured by aspect as the specification says — green for the start of a train route, yellow for the start of a shunting route, red for the end of a route, magenta while releasing and grey at rest. A route starting or ending at a `g` is always a shunting route, and neither type can be given go by hand, since there is no signal to give go.

- **Plain crossings** (*korsningar*) — a station file can now declare one in `[Points]` as `5.8(8-|29+)(29-|8+)`: the coordinate where two tracks cross, then one parenthesised way through it per track, each spelling the point position that lays that way, a `|`, and the positions that must hold while it is laid. Several conditions are separated by commas, and a comma between the ways is allowed. A crossing has nothing on it that moves, so this is the whole of it — which way is open is read off the points leading into it, and the conditions are what keep the other way clear.

  The conditions are enforced twice. At the keypad, laying a way is refused while a condition does not hold, and the refusal names the point that is in the way and says whether it is merely standing wrong or locked by a route. Since a point nothing has yet reported is as good as one standing wrong, laying a way over a crossing needs the other point turned away first — which is never itself refused, so the way out is always open. For routes, each way's conditions are added to every route that lays it, as flank protection, so the crossing is declared once instead of being written into each route by hand.

  On the diagram, the arms of a way that is not laid are broken by the same gap that shows a point turned away, cut parallel to the track that passes over. With both points straight the crossing is cut off on all four sides; with one of them thrown, its two arms join up and the other pair stays broken.

- **A break in a slanting track now follows that track** — the gap that shows a closed arm was measured straight up and down, which squares it against a track running level but leaves it skewed against one running at 45°, its ends horizontal where the rails are not. It is now measured along the arm it cuts, so it reads as a gap in that track whichever way the track runs. This shows at every arm of a plain crossing, where nothing runs level, and at a point standing straight, whose closed diverging arm is now broken square across and by the same width as every other break rather than by a long slanting lozenge. A closed arm that runs level is drawn exactly as before, which is most of them.

  Munkeröd's crossing at 5.8, where the diagonal carried by point 8 crosses the one carried by point 29, is now declared this way.

- **Platforms** — a station file can now declare passenger platforms under `[Platforms]` as `from,to:side`, where the coordinate pair names the stretch of track the platform serves and `u` puts it under that track on the diagram, `o` over it. A platform is drawn as a band half again as wide as the track, a shade darker than free track, and standing clear of the rails by a gap — mind the gap — so it reads as somewhere people stand rather than as track a train runs over. It carries no state and never changes colour, so it is drawn under every other layer and nothing on the diagram is hidden behind it. In the inverted view, which turns the whole yard half a turn, an *under* platform is drawn above its track: the same side of the same track, seen from the other end of the yard.

- **A single signal can be set from the keypad** — `S{signal}+` gives a signal go and `S{signal}-` puts it to stop, which is the keypad's form of what shift-clicking a signal on the diagram already did. `S` reads as *signal*, so the shunting area command took `A` for *area* instead. It asks nothing of the interlocking, so a signal no route covers can be worked too; a buffer stop is refused go, since §6.2.9 gives it no proceed colour. Signals are the dispatcher's alone. Previously the keypad could only set *every* signal to stop, with `**`.
- **Train numbers stand on the track, not at a signal** — a train number now sits on a detection stretch, the piece of track a train can be on, and is written centred above it. It is drawn in a monospaced face and padded with leading zeroes to five digits, so a yard full of them lines up and one can be told from another at a glance. Following EBICOS, the number is repeated along every stretch of the route the train is running, so each piece of track shows which movement it has been given to; the copies wear the colour of the stretch beneath them — red where the train actually stands, otherwise the colour of the route. Previously a single label sat beside the origin signal.
- **A train number marks its stretch occupied** — with no detector behind the diagram, the train number is what says where a train is, so the stretch it stands on is drawn red like any occupied stretch (§6.2.1 priority 2). It is shown whole whether or not it shares track with another: a train number names one stretch exactly, so there is nothing for the points to resolve. Detector state and train numbers are read side by side, so neither can erase the other.
- **A train number's life through the station is deduced from the commands given** — nothing on the layout reports one, so the application assumes a train follows the route it was given. Accepted from the previous station it stands on the run in from the layout edge; confirmed arrived it moves up to the stretch in front of the route's final signal; departed it steps out onto the run between the last signal and the edge; and reported arrived at the next station it leaves the diagram. `=[trainnumber]⏎` walks those steps one at a time.
- **A train can be handed over at the edge of the layout by naming the signal** — a dot beside the signal number now stands for the edge, and the side it sits on says which side of the signal the edge is on. `{signal}.=⏎` runs a departing train out past that signal onto the track leading off the layout, which until now only `=[trainnumber]⏎` could do — so a dispatcher who works the diagram by pointing at signals rather than by naming trains has a form for the last step too, and it ends the outbound route as an arrival does. `.{signal}=[trainnumber]⏎` puts a train the previous station has offered onto the run in from the edge before any route is set, and `{signal}.=[trainnumber]⏎` does the same on the outbound side, which is how a departed train is put back on the diagram after a restart. The topology decides which forms make sense: a signal the track does not leave the station through has nothing beyond it, so a train can never be sent out past an inbound signal nor accepted through an outbound one, and where a border coordinate carries a signal for each direction the dot says which of the two runs is meant. `.{signal}=⏎` is refused — back onto the track it came in on is the one direction a train number never goes.
- **Track detection stretches** (§6.2.1) — a station file can now declare *spårledningar* under `[OccupancySections]` as `number:from,to  @address`. A stretch is an isolated piece of track the hardware reports as occupied; it has no direction, and the feedback address is optional, so a stretch not yet wired to a detector can be declared and filled in later. Occupancy arrives as detector notifications — LocoNet `OPC_INPUT_REP` over serial, or the Z21's LocoNet and CAN detector broadcasts, for which the Z21 subscription now also asks for `OccupiedStretch`.
- **Occupied track is drawn red** (§6.2.1 priority 2) — above every route colour, so where a train stands the diagram says so before it says what the track was set for. In development there is no detector to report anything, so clicking a stretch reports it occupied or free instead; the click reports the shortest stretch covering the track under the pointer that the points still connect end to end.
- **The points say which overlapping stretch a detector is reporting** — stretches overlap at the points, where a detector cannot say which way through them the movement went, and showing every overlapping stretch would light the whole throat red. The points can say: one standing straight is turned away from its diverging arm, and that is what tells one stretch through a throat from the others sharing its rails. So an occupied stretch is drawn where its points still connect it — whole where they are set for it end to end, otherwise only the part a movement could still have reached. It holds whether or not a route is set over the track, so there is nothing to switch on and no setting to get wrong. A point whose position is not known is turned away from nothing, because not knowing where a point stands must never hide a train. Several stretches may now share one feedback address, which is what a throat's single detector really reports.
- **A first set of stretches is deduced from the topology** — a station file with no `[OccupancySections]` section at all gets one written into it, so only the addresses need filling in. The ends are the signal coordinates and the coordinates where track leaves the layout, and two signals standing back to back on one coordinate count as one end. A stretch runs between two ends that reach each other without passing a third, which means stretches overlap where the track branches — a train on a throat is on every stretch that runs over it. Munkeröd gets 171 stretches, Steinsnes 17. A file that already declares the section, even an empty one, is left alone: an empty section says the station has no detection, which is an answer rather than a gap to fill.
- **EBICOS signal symbols** — signals are now drawn with the symbol set from Trafikverket TRVINFRA-00305 "Rangerstyrsystem" §6.2.3–6.2.5 instead of a single pennant. A chevron is a dwarf signal (`d`), a pierced triangle is a main signal (`u`, `i`), and a main dwarf signal (`h`) draws both with the dwarf part on the approach side, so a train meets the chevron first. The symbol sits on the track centreline, breaks it, and points in the direction of travel.
- **Buffer stops** (§6.2.9) — a station file can now declare a *stoppbock* in `[Signals]` with the type marker `s` (`7.1:<47s` — the colon before the type marker may be left out). It marks the physical end of a dead-end track, so it can only stand at a track end that is not at the edge of the layout, where the track leaves the station instead of ending, and it must face the way the track leads up to it. It is drawn as the specification's bar across the track end with a stem leading back into it, turned to stand square to the rails wherever the track it closes runs on a diagonal: grey at rest, red as the end point of a movement, and never green, because §6.2.9 gives it no proceed colour. A movement may end at a buffer stop but never start there, so a route to one is always a shunting route, the diagram refuses it as a route's first tap, and it cannot be toggled to go — there is nothing beyond it to continue to.
- **Stored start point marker** — selecting the *from* signal now shows the specification's *magasinerad börjanpunkt*: a blinking green flag beneath the symbol, replacing the yellow outline.
- **Dispatcher and shunter views** — a station now has two views. `/{station}` (or `/`) is the dispatcher's, unchanged except that a released shunting area is no longer the dispatcher's to work; `/{station}/shunter` is the shunting yard master's, showing the whole yard but permitting only the released areas. A button in the footer switches between them. The shunter view takes no keyboard input, and shows one chip per shunting area with buttons to ask for an area, withdraw an unanswered request, or hand a released one back — an area can still only be *released* by the dispatcher, with `A{area}+`. A request appears in blinking blue under the dispatcher's diagram until it is answered.
- **The whole diagram can be worked by pointing** — for a tablet with no keys. Tapping a point label throws the point; the label carries a hit area wider than the text so a finger finds it. Tapping the signal a route starts from asks to clear that route, and a second tap on the same signal clears it. Tapping the destination signal of a route that no other signal follows toggles that signal between stop and go — those signals can only end a movement, so the tap is unambiguous. Setting a route by tapping two signals worked already. CTRL+click and Shift+click still do what they did.
- **A released shunting area belongs to the shunter alone** — the interlocking now refuses the dispatcher a point in a released area, a point coupled to one by a slave cascade, and any route that would use one. The shunter may work only those points, and only routes that stay inside the released areas, which may cross from one released area into another. Such a route is always set as a shunting route, whatever its signals would otherwise allow. Every keystroke and every tap carries the role that made it, so the rules hold in the input pipeline rather than in the buttons a view happens to show.
- **Taking an area back clears what is standing in it** — `A{area}-` now clears any active route that uses one of the area's points before releasing its flank protection, so the area returns to the interlocking in a known state.
- **Shunting areas** — a station file can declare named groups of points under `[ShuntingAreas]` (`number:name:point[,point…]`) that are handed over to a shunter as a unit. `A{area}+` releases an area, `A{area}-` takes it back. A released area's points are drawn in EBICOS blue (§6.2.12 priority 9, *ingår i växlingsområde*), which is the notation for "the shunter decides where these stand, not the interlocking". A point declared with a `+` or `-` suffix is flank protection: it is set to that position and held locked for as long as the area is released, so nothing can run into the area, and it keeps the normal grey because it is not the shunter's to move. A release is refused while any of the area's points is locked by an active train route.

### Behaviour changes

- **Each view now shows only its own operator's messages** — with the dispatcher's view open on one screen and the shunter's on another, both status lines used to report every command given anywhere in the yard, so each operator read a running commentary on work that was not theirs. A message is now addressed to whoever gave the command that caused it, and shown only there: a route the shunter set names nothing the dispatcher can act on, and a refusal belongs to the person who was refused. Three things still go to both, because the other operator must be told whatever caused them: clearing the whole yard with `//` or `ESC ESC`, which takes down the shunter's routes as much as the dispatcher's; a shunting area released, taken back, or asked for; and anything the hardware reports of its own accord. The line under the diagram showing a command as it is typed follows the same rule, and with it the blinking of the signals still matching the digits — a shunter's diagram no longer flickers at the dispatcher's typing. Only the words are addressed: every route, point and signal is still drawn on both diagrams whichever of the two moved it, since they are looking at the same tracks.
- **The yard can be worked from another computer on the network** — the application now listens on port 5180 on every network interface instead of on `localhost` alone, so a second computer or a tablet on the same local network can open it: one operator at the dispatcher's view, another at the shunter's. The addresses it answers on are written to the log at startup, since `0.0.0.0` is not something anyone can type into a browser. The port and the interfaces are set in `appsettings.json` under `Kestrel:Endpoints`, which is now the one place the binding is decided. Only plain HTTP is served — HTTPS redirection and HSTS are gone, because a certificate would have to be valid for whatever address the operator types, which on a layout network is an address handed out by DHCP. The application is meant for a closed layout network, never for the open internet.
- **`[signal]=⏎` only moves a train forward** — it now moves the train number up to the detection stretch in front of the given signal, and refuses a signal that is not on the route the train is running or that lies behind where the train stands. Which stretch is *in front of* a signal follows the direction the train runs, not the direction the signal faces: a route runs past signals for the opposite direction, and a train coming up to one of those stands on the stretch behind it, not the one beyond it. Previously it moved the number from a route's origin signal to its destination signal with no check on direction.
- **`[signal]=[trainnumber]⏎` places the number on a stretch** — the number goes on the detection stretch leading up to the signal rather than on the signal itself, which is how a train that is not running a route is put on the diagram. Where the track branches several stretches end at one signal: an active route running over that signal decides which, and without one the shortest approach stretch is taken — the track alongside the signal rather than a run across the whole throat.
- **Reporting a train arrived or departed clears its route** — a route is set for one movement, and that movement is over the moment the train is reported at the route's final signal, so the route is now torn down there and then. Both `=[trainnumber]⏎` and `[signal]=⏎` up to the route's own final signal do it, which is what `[signal]/` already did. Reporting the train departed does the same for the outbound route it left on, and puts the number on the stretch from the last signal out to the layout edge, which is drawn occupied like any stretch a train stands on. Previously the route stayed set behind the train until the dispatcher cleared it by hand.
- **A train reported arrived releases the point locks without the delay** — `LockReleaseDelay` protects a route torn down while a movement may still be running on it, which is every teardown the operator asks for: `[signal]/` and `//` say no more about where the train is than `ESC` and `ESC ESC` do, so all four still hold the locks and show the route magenta while the delay counts down. Reporting the train at the route's final signal is different — it says the train is standing there, clear of the points — so a route ended by `=[trainnumber]⏎` or `[signal]=⏎` releases its locks at once. Shunting routes release immediately as before.
- **`=[trainnumber]⏎` gained a step at the edge of the layout** — a train standing at an outbound signal with no route left now moves onto the run between that signal and the layout edge, where a departed train stands, and only the press after that takes it off the diagram. Previously it was removed as soon as no further signal existed, so a departed train could not be shown.
- **A shunting route leaves main signals at stop** — every signal a shunting route passes, the from signal included, is now cleared only if it has a dwarf part. A main signal (`u`, `i`) has no shunting aspect and stays at stop; a main dwarf signal (`h`) is cleared and shows *stopp i huvudsignal, lodrätt i dvärgsignal* — green dwarf part, grey main part. Previously only the from signal was checked, and only when it was an inbound main signal, so intermediate signals went fully green.
- **A main route from a shunting signal becomes a shunting route** — a shunting dwarf signal (`d`) can only authorise a shunting movement, so a route requested with `⏎` from such a signal is now set as a shunting route instead of a main one. This applies to composite routes as well, where the first signal decides. Consequently the destination outbound main signal is not cleared to go, and the locks release without the safety delay. Previously the route was set as a main route.
- **A signal at stop is grey, not red** (§6.2.3–6.2.5) — red is now reserved for the destination signal of an active route (*slutpunkt/stopp i rörelseväg*). An idle yard reads as calm; an active route stands out. A main dwarf signal colours its two halves independently, so a shunting route shows a green dwarf part against a grey main part, exactly as the specification's *"stopp i huvudsignal, lodrätt i dvärgsignal"* describes.
- **Signal numbers moved outside the symbol** (§6.3) — object text for signals is yellow, centred above the symbol for a signal facing right and below it for one facing left, which encodes direction without extra ornament. Previously the number was reversed out in white inside the symbol.
- **Point labels are magenta** (§6.3, K126529) — was light blue (`#aaddff`).
- **Train numbers are bare coloured text** — placed above the track on the approach side of the signal and coloured by the route the train is on (green for a train route, yellow for shunting, magenta while releasing, white when no route is set). Previously a blue box abutting the signal.
- **A train number is written along the track, not across it** — a stretch runs level or at 45°, and most of them run both in turn, so a number placed at the plain middle of its stretch could land over a slope and read as belonging to neither of the tracks it slanted between. Each number is now set along one straight run of its stretch and turned to that run's angle: level wherever the stretch has a level run — at Munkeröd that is 170 of its 171 stretches, the shortest run a whole cell, which carries five digits with room to spare — and along the rails at 45° for the one stretch that never runs level. The gap between the text and the rails is measured square to the track, so a number over a slope keeps the same clearance its whole length. The magenta dot on a stretch held occupied by hand is placed the same way, and now always sits on the rails instead of alongside them.
- **Status messages carry the colour of what they are about** — the line under the diagram is now green for a train route, yellow for a shunting route, magenta for a route being released and for a point, and blue for a shunting area, so the words say what the tracks and symbols are already showing. A refused command stays red whatever it regards. Previously every successful command was green, every point message borrowed the route colours, and taking a shunting area back reported itself in magenta. The queued-routes line follows the same rule per entry — each queued route is drawn in the colour of the route it is waiting to become, instead of the whole line turning yellow.
- **A shunting route is called a shunting route** — every message about a route now names its kind: *shunting route* (*växlingsväg*, *rangervej*, *skiftevei*, *Rangierstraße*) for a shunting movement and *train route* (*tågväg*, *togvej*, *togvei*, *Zugstraße*) for a train movement. Previously all of them said train route, and the German used the generic *Fahrstraße* for both.
- **Exact palette values adopted** (§6.1) — free track and signals at stop `#969696`, train routes `#008000`, shunting routes `#FFFF00`, route destination `#FF0000`, releasing `#FF3399`. Cancelling routes were purple (`#aa44ff`); train routes and shunting routes previously used approximations (`#00cc00`, `#ffcc00`).
- **Track section gaps are drawn as a break in the line** — the specification shows a section boundary as a break rather than a coloured mark, and reserves orange for hump routes, so the orange tick is gone.

### Bug fixes

- **A train number no longer disappears when it cannot be advanced** — `=[trainnumber]⏎` used to treat *I cannot work out where this train goes* as *this train has left the layout* and take the number off the diagram. A train standing at the from signal of a route it has been given is running that route and has not left the station, whatever the track around it looks like — the stretch it waits on is a run in from the layout edge at every inbound signal, so nothing about the track itself tells the two apart. The command is now refused and logged, and the train stays where it stands.

- **Munkeröd's detection stretches match its signals again** — the stretches under `[OccupancySections]` are deduced once and then kept, so the signals added and moved since they were written left them describing the yard as it used to be: nothing ended at signal 30, at signal 99, or at the new coordinates of 37 and 68. A route to such a signal had no destination stretch, which is what made a train run over it vanish. The stretches have been regenerated, and the parser now warns about a signal no stretch ends at, so a file that has gone stale says so at load time rather than at the diagram.

- **Munkeröd route 38-30 was declared as 30-30** — a route from a signal to itself, which is what a mistyped signal number looks like. A composite route silently leaves out a part that is not declared rather than refusing to be built, so routes 22-30 and 38-42 were being set without point 9, the point the missing part was there to throw.

### Documentation

- **Corrected clear/cancel description** — the README stated that cancelling (`ESC`) releases point locks immediately. Both clearing (`/`) and cancelling hold the locks for `LockReleaseDelay`; only a shunting route, or a route ended by reporting the train at its final signal, releases without delay. The difference between the two commands is what happens to the train number, not to the locks.

## Version 1.2.0

### New features

- **Coupled-point cascade (single-slip support)** — `[Points]` lines may now declare slave clauses (`&<masterPos>:<slave><slavePos>[,...]`) so that setting one point automatically sets another. Setting a master point on the keypad cascades to all slaves; routes that include a master point are auto-expanded with the slave commands at load time. Routes or commands that would force a single point to two different positions are hard-rejected with a clear error.
- **Revised train number lifecycle** — train numbers now stay where the train physically is. `=[trainnumber]` on a route-set assigns the number to the **origin** signal (previously: destination). Three new arrival commands let the operator advance the number explicitly:
  - `[signal]/` — clear the route up to that signal AND move the train number there
  - `[signal]=⏎` — move the train number to that signal without clearing the route
  - `=[trainnumber]⏎` — advance that train one signal forward along its current route, or remove it if there is no further signal (e.g. next station confirms arrival from an outbound signal)
- **Train number visible at outbound signals** — clearing a route to an outbound main signal now keeps the train number visible at the outbound until next-station arrival is confirmed via `=[trainnumber]⏎` (previously: removed immediately).
- **Train number on queued routes** — when a route is queued due to a conflict, the queued-routes display now shows the train number alongside the signal pair.
- **EBICOS-aligned colour palette** — inactive track is now light gray (was white) and shunting routes are yellow (was orange). Train routes remain green; cancelling routes remain blue.

### Behaviour changes

- **Active route takes precedence over queued route** — when both an active and a queued route exist to the same signal, `[signal]/` clears the active one first (previously: cancelled the queued one).
- **Cancel of non-existent route is silently ignored** — `[signal]/` and `[signal]ESC` produce no message when no route ends at that signal (previously: error feedback).

### Bug fixes

- **File watcher catches editor saves** — auto-reload of station files now subscribes to `Created` and `Renamed` events in addition to `Changed`, so editors that save atomically (Visual Studio, VS Code) trigger reload.
- **`=[trainnumber]⏎` is now deterministic** — when a train number existed at multiple signals (e.g. after re-setting a route over a previously-arrived train), the advance command would non-deterministically pick one. It now prefers the signal that is the origin of an active route.

## Version 1.1.0

### New features

- **Z21 command station support** — The application can now connect to a Roco/Fleischmann Z21 directly over UDP, in addition to LocoNet over serial. Select the command station with `CommandStation:Type` in `appsettings.json` (`"Serial"` or `"Z21"`).
- **Full interoperability with Z21 App and WLANMaus** — When using the Z21, point changes from the yard app are visible in the Z21 App and WLANMaus, and vice versa. All clients stay in sync regardless of who initiated the change.
- **Single-executable publish** — Release archives now contain a single executable plus the `Data` and `wwwroot` folders, instead of dozens of DLLs.

### Breaking configuration change

- The top-level `"SerialPort"` section in `appsettings.json` has been replaced by a nested `"CommandStation"` section:
  ```json
  "CommandStation": {
    "Type": "Serial",
    "SerialPort": { "PortName": "COM5", "BaudRate": 57600 },
    "Z21": { "Address": "192.168.0.111", "CommandPort": 21105, "FeedbackPort": 21106 }
  }
  ```
  Existing installations need to update their `appsettings.json` when upgrading. UDP port 21106 must be allowed through Windows Firewall for Z21 feedback to work.

## Version 1.0.0

First public release of the Yard Control Application.

### Features

- **Interactive web UI** — SVG-based yard diagram with clickable signals, colour-coded point positions, and active route highlighting (green for main routes, orange for shunting routes, blue during cancellation).
- **Signal-based train route setting** — click a from-signal and a to-signal to set a route; the application moves and locks all required points automatically.
- **Automatic route derivation** — routes can be fully derived from the yard topology graph, requiring only the from and to signal numbers in the configuration.
- **Main and shunting routes** — shunting routes use dwarf signals, skip destination signal go-aspects, and release locks immediately.
- **Train number labels** — assign train numbers to signals and see them displayed live on the yard diagram. Numbers follow the train automatically as routes are set.
- **Clear vs cancel semantics** — clearing a route keeps train numbers and releases locks after a safety delay; cancelling removes train numbers and releases locks immediately.
- **Multiple station support** — configure several stations and switch between them at runtime. Each station opens in its own browser window.
- **Unified station configuration** — define the entire station (topology, points, signals, routes, translations) in a single human-readable text file.
- **Flank protection** — routes can include flank protection points that are locked but not on the active path.
- **Point locking** — logical locking prevents conflicting routes; optional hardware locking via configurable address offset for Mollehem switch decoders.
- **Signal control** — signals are set to go/stop automatically when routes are set or cleared. Five signal types supported: OutboundMain, InboundMain, MainDwarf, ShuntingDwarf, and Hidden.
- **Train route queueing** — when a route conflicts with an active route, it is automatically queued and executed as soon as the blocking route is cleared or cancelled. Queued routes are shown in the UI and can be cancelled before they execute.
- **All Signals Stop** — emergency button to immediately set all signals to red.
- **Reset all points** — set all unlocked points to straight position with a single command.
- **Numeric keypad input** — all operations can be performed from a numeric keypad for hands-free wireless control.
- **Turntable control** — move turntable to specified track positions via numpad commands.
- **LocoNet integration** — point commands, signal control, and position feedback via LocoNet protocol.
- **Real-time position feedback** — point changes from any source (other throttles, apps) are reflected in the UI.
- **Live configuration reload** — edit data files while the application is running; changes are detected and applied automatically.
- **Localisation** — UI and track labels available in English, Swedish, Danish, Norwegian, and German.
- **Serial port validation** — startup diagnostics for LocoNet hardware connectivity in production mode.
